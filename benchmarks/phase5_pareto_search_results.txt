Reading (see docs/PARETO_SEARCH.md and docs/BENCHMARK_PLAN.md's Phase 5 addendum for the
full discussion):

1. Label growth across tiny -> small -> medium is real but not explosive at these sizes
   (19 -> 35 -> 154 inserted labels), and dominance comparisons grow faster than labels
   inserted (72 -> 112 -> 2401) -- consistent with ALGORITHMS.md §6's O(n) per-insertion
   dominance-check cost compounding as the surviving set at each node grows.

2. The 'larger' scenario (5 stages, realistic 2.5 km/s vehicle budget) is fully
   UNREACHABLE -- every route's cumulative delta-v exceeds the budget by the time it
   reaches the target, correctly rejected by the cumulative delta-v hard constraint this
   phase exists to enforce. This is itself a real, reportable finding, not a benchmark
   defect: it demonstrates the hard constraint firing on a scenario deep enough for
   accumulated cost to matter, exactly the failure mode Dijkstra/A* could not detect at
   all (ParetoSearch.CumulativeDeltaVHardConstraintRejectsWhatDijkstraWronglyAccepts,
   pareto_search_test.cpp).

3. Epsilon-dominance collapses the frontier sharply and monotonically as epsilon grows:
   19 -> 3 -> 2 -> 1 -> 1 routes at epsilon = 0 (exact), 0.02, 0.05, 0.10, 0.20. Dominance
   comparisons and wall-clock time both drop in step (2401 -> 117 -> 66 -> 54 -> 46
   comparisons; ~0.049ms -> ~0.009ms median at epsilon=0.20 -- roughly a 5-6x speedup).
   This is the expected, documented behaviour of ε-dominance (ALGORITHMS.md §5.7): treating
   near-identical labels as dominated trades completeness for size, and the trade is
   visible and substantial even at a small epsilon (0.02) on this scenario.

4. Whether the RECOMMENDED plan changes under epsilon-dominance was not measured in this
   run -- MissionScorer operates on a ParetoFront, and this benchmark measures the raw
   `algorithms::findParetoRoutes()` layer only. This is a reasonable Phase 5+ extension
   (score the exact vs each epsilon front under a fixed profile and compare which plan
   wins), not built here, and not claimed to have been checked.

Scope and honesty notes:
 - 4 scenarios x 1 seed each x 10 reps -- a micro-benchmark demonstrating real, measured
   trends, not a statistically powered study.
 - Scenario topology (a "fan": several structurally distinct candidate orbits per stage,
   fully connected between consecutive stages) was chosen specifically because a single
   backbone (Phase 4's topology) rarely retains more than one or two labels per node --
   see PARETO_SEARCH.md's discussion of how much deliberate search went into finding
   genuine multi-way trade-offs from real orbital parameters.
 - No number in this file was hand-derived or estimated -- every figure is copied from a
   real run of the compiled program named above.
